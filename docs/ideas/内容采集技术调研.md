# 内容采集技术调研

## 结论

不存在“自动化采集小红书且保证不被封禁”的可靠技术方案。更现实的做法是把内容采集设计为多数据源、低频、可追溯、人工辅助的模块，优先解决后续拆解、选题评分、内容生成和复盘所需的数据输入。

第一版不建议做高频爬虫、逆向 App 接口、验证码绕过、Cookie 池、代理池、设备指纹伪装或无人值守批量抓取。这些方案短期看起来能拿到数据，但工程维护成本高、账号风险高、合规风险高，也不利于团队长期使用。

## 推荐采集路径

### 1. 人工导入链接

运营人员把竞品笔记链接、博主主页链接、关键词搜索结果链接放入系统，采集模块只负责解析、归档和后续处理。

优点：
- 开发最简单。
- 风险最低。
- 适合快速验证“拆解、评分、生成”链路。

缺点：
- 自动化程度低。
- 数据规模依赖人工筛选。

适合 MVP 第一阶段。

### 2. 浏览器插件辅助采集

做一个内部浏览器插件。运营人员正常浏览小红书时，点击“保存当前笔记”或“保存当前搜索结果”，插件把页面中可见的标题、正文、作者、互动数据、图片链接、评论摘要等保存到本地采集服务。

优点：
- 是人工浏览行为的增强，不是无人值守爬虫。
- 可控、可审计、可解释。
- 非常适合做竞品内容库。

缺点：
- 需要开发插件。
- 页面结构变化时需要维护解析逻辑。
- 仍然要遵守平台规则，不能做批量自动翻页和大规模后台采集。

建议作为第一版的主采集方式。

### 3. RPA 人工辅助采集

使用 Playwright、Chrome DevTools 或桌面 RPA，在运营人员登录后执行低频任务，例如打开一批已收藏链接、截图、复制可见文本、保存基础指标。

边界建议：
- 必须由人工触发。
- 不自动绕过验证码。
- 不做登录态盗取或 Cookie 导出。
- 不做代理池/IP 轮换。
- 不做夜间无人值守批量抓取。
- 对每个账号、关键词和页面设置严格频率限制。

优点：
- 比插件更容易快速实现。
- 可以复用浏览器可见内容。
- 适合跑小样本实验。

缺点：
- 稳定性一般。
- 页面改版容易失效。
- 规模化后风险上升。

适合验证期，不适合做长期核心数据管道。

### 4. 第三方合规数据服务

采购小红书数据服务商的数据能力，例如博主监控、笔记搜索、关键词趋势、互动数据等。

优点：
- 数据稳定性通常更好。
- 更适合长期运营和批量监控。
- 能减少自研采集风险。

缺点：
- 成本更高。
- 数据口径需要验证。
- 合规责任和授权范围要审查。

适合后续进入真实运营阶段后接入。

### 5. 官方后台和自有账号数据

对自己账号发布后的数据，优先通过创作者后台、人工导出、截图识别或授权数据工具采集。复盘学习模块最需要的是自有账号表现数据，这部分比竞品数据更重要。

优点：
- 最贴近涨粉目标。
- 可用于训练团队自己的内容判断。
- 风险低于抓取外部博主数据。

缺点：
- 冷启动阶段数据少。
- 导出能力受平台后台限制。

应从第一版就纳入数据模型。

## 不建议做的方案

- 高频网页爬虫：小红书 robots.txt 对通用抓取为 `Disallow /`，且平台内容页反爬强，长期不稳定。
- 逆向 App 接口：维护成本高，风险高，不适合作为内部长期产品基础。
- Cookie 池：账号安全和权限审计问题严重。
- 代理池/IP 轮换：本质是在对抗风控，不适合作为合规产品能力。
- 自动绕过验证码：不应实现。
- 无人值守搜索、翻页、批量保存：容易触发平台风控，也会污染后续数据质量。

## MVP 采集模块设计

建议先做一个独立 CLI/本地服务，不做 Web。

技术栈：
- Go
- SQLite
- WAL
- 本地文件存储图片和截图
- 可选 Playwright/RPA 作为外部采集器

命令形态：

```bash
xhs-tool source add --type note --url "https://www.xiaohongshu.com/..."
xhs-tool source import --file links.csv
xhs-tool collect parse --source-id 123
xhs-tool collect snapshot --source-id 123
xhs-tool collect list --status pending
```

核心表：

```sql
sources(id, type, url, platform, status, created_at, updated_at)
raw_pages(id, source_id, html_path, screenshot_path, text_path, captured_at)
notes(id, source_id, author_name, title, body, tags, like_count, collect_count, comment_count, published_at, captured_at)
assets(id, note_id, asset_type, local_path, source_url, created_at)
collection_runs(id, mode, status, started_at, finished_at, error)
```

第一阶段只要求采到：
- 笔记链接
- 标题
- 正文
- 作者
- 发布时间或可见时间
- 点赞/收藏/评论等可见互动数
- 图片 URL 或截图
- 来源页面截图
- 采集时间

不要在第一阶段追求评论全量、粉丝画像、博主全量笔记、关键词全量搜索结果。

## 推荐实验顺序

1. 人工导入 50 条竞品笔记链接。
2. 手动或插件保存页面可见文本和截图。
3. 用拆解模块验证这些数据是否足够产生选题。
4. 如果数据不足，再补 RPA 打开链接并截图/复制内容。
5. 如果团队开始真实高频使用，再评估第三方数据服务。

## 判断标准

采集模块第一阶段的成功标准不是“抓得多”，而是：

- 每条数据有来源和截图，可追溯。
- 采集结果足够支撑内容拆解。
- 运营人员愿意每天提供或保存参考笔记。
- 账号和登录态没有异常风险。
- 页面结构变动时修复成本可控。
