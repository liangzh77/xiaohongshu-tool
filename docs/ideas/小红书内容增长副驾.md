# 小红书内容增长副驾

## Problem Statement

我们如何帮助内部运营团队从行业博主和竞品内容中快速发现可做选题，并把选题转化为可审核、可发布、可复盘的小红书内容方案，从而提升账号涨粉能力，而不是制造高风险的批量搬运内容？

## Recommended Direction

建议把产品定位为 **小红书内容增长副驾**，核心不是“全自动运营”，而是“选题雷达 + 内容工坊 + 人审发布台”。系统每天围绕指定行业、关键词、竞品博主和账号定位，产出高质量选题、爆文结构拆解、内容草稿、封面建议和发布复盘，让运营人员在很短时间内完成判断、修改和发布。

这个方向比全自动养号/发布更适合作为第一版。原因是涨粉的关键通常不在于自动点击和批量发布，而在于选题是否击中用户需求、内容是否有可信表达、账号定位是否稳定、复盘是否能沉淀经验。自动化应该先服务于“更快做出好内容”，而不是替代运营人员做所有决策。

OpenClaw 适合作为自动化执行和流程编排层，例如定时任务、浏览器辅助、截图、表单填充、日报推送、多 agent 协作。但核心业务系统应独立建设，包括数据存储、内容工作流、权限、审计、提示词版本、素材库和复盘模型。这样既保留 OpenClaw 的灵活性，也避免把重要资产锁在 agent 临时上下文里。

## Product Shape

第一版产品由六个模块组成：

- 行业情报库：维护竞品博主、关键词、行业标签、目标人群、账号定位和禁区词。
- 内容采集层：优先支持人工导入、浏览器插件采集、第三方数据服务、创作者后台数据和运营人员收藏链接；不建议做高频全站爬虫。
- 爆款拆解器：把参考笔记拆成选题类型、标题公式、开头钩子、用户痛点、情绪触发点、内容结构、转化方式、可借鉴点和不可照搬点。
- 选题评分器：按账号匹配度、近期热度、素材可得性、涨粉潜力、差异化空间、合规风险和同质化风险排序。
- 内容生成器：输出标题、开头、正文、封面文案、图片脚本、标签建议和发布注意事项，供人工选择和修改。
- 复盘学习器：记录每篇笔记的选题、标题、封面、正文结构、发布时间和表现数据，让系统逐步学习团队自己的有效内容模型。

## MVP Scope

MVP 只做一个闭环：

运营人员配置 20 个竞品博主和 20 个关键词，系统每天生成一份“小红书选题日报”。每个选题包含参考来源、选题理由、用户需求判断、参考笔记拆解、内容角度、标题候选、正文草稿、封面建议、标签建议和风险提示。运营人员可以在 10 分钟内选出当天要做的内容，并进入编辑与发布准备。

MVP 的目标不是证明“AI 可以自动运营小红书”，而是证明“AI 能显著缩短运营从调研到成稿的时间，并提升选题质量”。

## Suggested Technical Architecture

- Web App：团队工作台，负责选题日报、内容编辑、审核状态、素材库、数据复盘。
- Backend API：管理账号定位、竞品库、采集任务、内容生成任务、审核流和数据指标。
- Database：PostgreSQL 存结构化数据，pgvector 或向量库保存笔记拆解、选题 brief 和历史表现语义索引。
- Queue/Scheduler：负责每日采集、拆解、生成日报、复盘任务。
- LLM Layer：封装模型调用、提示词版本、输出结构校验、违规风险检测和多版本生成。
- OpenClaw Layer：负责定时触发、浏览器辅助、截图采集、打开创作页面、把日报推送到团队沟通工具。
- Asset Layer：保存图片素材、封面模板、AI 生成图、人工上传素材和使用记录。

## Data & Compliance Boundary

不要把第一版建立在“绕过平台限制的大规模爬虫”上。小红书 robots.txt 对通用抓取是 `Disallow /`，高频抓取公开页面和无人值守自动发布都存在平台风控、账号安全和合规风险。

建议采用更稳的采集路径：人工收藏链接、浏览器插件辅助采集、运营人员登录态下的低频个人工作流、创作者后台数据、第三方合规数据服务、手动导入 CSV。系统应保留来源链接、采集时间、处理记录和人工审核记录。

AI 生成图片、视频或深度合成内容时，需要考虑 AIGC 标识和平台规则。团队内部产品也应默认保留生成记录、素材来源、模型版本和审核人，避免后续无法追溯。

## Key Assumptions to Validate

- [ ] 运营团队真正缺的是高质量选题判断，而不是单纯缺文案。测试方式：让 2-3 名运营连续使用 5 天选题日报，记录他们是否真的采纳系统选题。
- [ ] 竞品内容的主要价值在于结构拆解和需求洞察，而不是原文复制。测试方式：对比“参考原文改写”和“拆解后重写”的发布质量与人工评价。
- [ ] 人工审核不会显著拖慢流程，反而会提升团队信任。测试方式：记录从日报生成到最终成稿的平均耗时。
- [ ] 账号定位和历史表现数据能明显提升生成质量。测试方式：对比通用提示词输出和带账号定位/历史数据输出的运营评分。
- [ ] 低频、合规、可追溯的数据采集足够支撑第一版价值。测试方式：先用人工导入和插件采集跑通，而不是先做复杂爬虫。

## Not Doing (and Why)

- 自动养号：风险高，和“涨粉”的核心因果关系弱，容易把产品带向灰色自动化。
- 无人值守自动发布：第一版需要人工审核内容质量、事实准确性、商业表达和平台风险。
- 承诺涨粉比例：涨粉受账号基础、行业、人设、素材、发布时间和平台流量波动影响，早期不应定量承诺。
- 训练所谓爆文模型：MVP 阶段数据量不够，先用结构化拆解、规则评分和人工反馈闭环更现实。
- 全站高频爬虫：平台限制和账号风险过高，且不是验证 MVP 价值的必要条件。
- 多账号矩阵联动：会扩大复杂度和风控面，应该等单账号/少量账号工作流稳定后再做。

## First Build Milestones

1. 第 1 周：定义账号定位模型、竞品库、选题日报格式、笔记拆解 JSON schema。
2. 第 2 周：实现人工导入/链接采集、笔记拆解、选题评分和日报生成。
3. 第 3 周：实现内容生成工作台，包括标题、正文、封面文案、图片脚本和风险提示。
4. 第 4 周：接入人工审核、发布记录、基础复盘数据和 OpenClaw 定时推送。

## Open Questions

- 第一批内部账号的行业和定位是什么？
- 团队现在每天实际发多少篇，平均一篇从选题到发布耗时多久？
- 是否已有可用的竞品博主清单和历史内容数据？
- 是否允许接入第三方小红书数据服务？
- 发布动作是否必须进入系统，还是先只做到发布前内容准备？
